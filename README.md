# ProcurementSystem

## โมดูลขอใช้งบประมาณ (ต้นแบบ)

เปิดใช้งานได้ที่ `index.html` (รองรับ GitHub Pages โดยไม่ต้องมี backend) — หน้าทดสอบเดิมย้ายไปที่ `test.html`

> ระบบนี้ **ไม่ใช่การขออนุมัติงบ** — งบได้รับอนุมัติมาแล้ว ระบบใช้ **ตรวจสอบ (verify) ว่าใช้ถูกตัวงบ**
> และให้ผู้ใช้งบรู้ว่างบของตนเหลือเท่าไร

ใช้เมนู **"เข้าใช้งานในฐานะ"** มุมขวาบนเพื่อสลับผู้ใช้ตัวอย่างตามบทบาท

| บทบาท | ทำอะไรได้ |
| --- | --- |
| ฝ่ายการเงิน | บันทึก/แก้ไขงบลงทุน (CAPEX) และงบโครงการ (CBS) ที่ได้รับอนุมัติแล้ว, รับเอกสาร CAPEX และตรวจสอบ แล้ว *อนุมัติ* หรือ *ไม่อนุมัติ (แจ้งเหตุผล)* |
| ผู้ขอซื้อ / ผู้ขอใช้งบ | ตรวจสอบงบที่ใช้ได้ของตนเอง (*งบที่ได้รับ / ใช้แล้ว / รอตรวจสอบ / คงเหลือ*) และจัดทำเอกสารขอเบิกใช้งบโดยระบุตัวงบทุกครั้งที่จะใช้ |

### กระบวนการขอเบิกใช้งบลงทุน (CAPEX)
1. ผู้ขอซื้อตรวจสอบงบที่ใช้ได้
2. จัดทำเอกสาร (สินทรัพย์, จำนวน, อายุการใช้งาน, ใบเสนอราคา (ถ้ามี), เหตุผลความจำเป็น) → ส่งให้ฝ่ายการเงิน
3. ฝ่ายการเงินรับเอกสารและตรวจสอบ
   - **อนุมัติ** → ผู้ขอซื้อได้รับ *เอกสารการเบิกขอใช้งบประมาณ* → จบกระบวนการ
   - **ไม่อนุมัติ** → แจ้งเหตุผล → ผู้ขอซื้อ *แก้ไขและส่งใหม่* (ใช้เลขที่คำขอเดิม เก็บประวัติรอบก่อน) หรือ *ยกเลิก*

### กระบวนการขอเบิกใช้งบโครงการ (CBS)
1. หน่วยงานที่ขอซื้อตรวจสอบงบที่ใช้ได้ (แยกตามรายการต้นทุน — Cost Breakdown)
2. จัดทำเอกสาร (เลือกรายการต้นทุน, งาน/งวดงาน) → ได้ *เอกสารการเบิกขอใช้งบประมาณ* ทันที → จบกระบวนการ
   (ไม่ต้องผ่านฝ่ายการเงิน)
3. ถ้าทำเอกสารผิด (เช่น เลือกตัวงบ/รายการต้นทุนหรือยอดผิด) ผู้ขอ *ยกเลิกเอกสาร* ได้เองโดยต้องระบุเหตุผล
   → ยอดคืนเข้างบทันที และเลขที่เอกสารนั้นใช้แนบขอซื้อไม่ได้อีก

### ยอดคงเหลือ
- เอกสาร CAPEX ที่ส่งแล้วจะ **จองงบ** ทันที เพื่อให้ยอดคงเหลือที่เห็นตรงกับความจริง; ไม่อนุมัติหรือยกเลิกจะคืนยอดอัตโนมัติ
- ระบบไม่ให้ระบุยอดเกินคงเหลือ (กันการกรอกผิด)
- การเงินแก้ไขวงเงินให้ต่ำกว่ายอดที่ใช้/จองไปแล้วไม่ได้ และลบงบที่มีรายการแล้วไม่ได้

### เอกสารผลลัพธ์
*เอกสารการเบิกขอใช้งบประมาณ* เลขที่ `CAPEX-ปี-ลำดับ` หรือ `CBS-ปี-ลำดับ` พร้อมสรุปยอดงบก่อน/หลังใช้
(CAPEX มีผู้ตรวจสอบจากฝ่ายการเงิน) — พิมพ์หรือบันทึกเป็น PDF เพื่อแนบกับใบขอซื้อ (PR)

### ข้อจำกัดของต้นแบบ
- ข้อมูลเก็บใน `localStorage` ของเบราว์เซอร์ จึงไม่แชร์ข้ามเครื่อง/ผู้ใช้จริง และไม่มีการยืนยันตัวตน
- ก่อนใช้งานจริงควรมี backend + ฐานข้อมูล, ระบบล็อกอิน, และเชื่อมเลขที่เอกสารการเบิกขอใช้งบเข้ากับขั้นตอนขอซื้อ (PR)
